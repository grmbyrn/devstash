- 2026-07-24 — **Rate Limiting for Auth** (Completed). Added Upstash-backed rate limiting across the whole auth surface (brute force / credential stuffing / email-send abuse). New `src/lib/rate-limit.ts`: a lazy Upstash Redis client (`undefined`=unresolved / `null`=unconfigured) + a cached sliding-window `Ratelimit` per config, driven by a `RATE_LIMITS` table (`login` 5/15m, `register` 3/1h, `forgotPassword` 3/1h, `resetPassword` 5/15m, `resendVerification` 3/15m — mirrors the spec). `checkRateLimit(name, identifier)` returns `{ success, remaining, reset, limit }` and **fails open** (returns an `ALLOW_UNLIMITED` sentinel when Upstash is unconfigured *or* the `.limit()` call throws) so a Redis outage can never lock users out. **Four decisions were the user's, all settled at `start`:** (1) **`@aws-sdk/client-s3`**, no presigner — R2 is S3-compatible and hand-rolling SigV4 wasn't worth it. (2) **The bucket stays private and `Item.fileUrl` holds the object *key*, not a URL.** Every read — image previews included — goes through an authenticated proxy, so a leaked key grants nothing; `R2_PUBLIC_URL` is consequently unused by the code and left in the env for the day a bucket is deliberately public. This was chosen over the spec's implied public-URL-plus-download-proxy, which is a different trust model: a public bucket URL is a permanent unauthenticated link to a user's file. (3) **Upload through our own route** rather than presigned PUT, matching the spec and the coding standards' "API routes when you need file uploads with progress tracking" — with the Vercel ~4.5 MB serverless body cap accepted and recorded as a known limit on the 10 MB tier. (4) **Best-effort R2 delete when a create fails** behind a successful upload.

**The design is in two places.** `uploads.ts` holds every rule and no I/O — tiers, extensions, MIME derivation, `fileUrlForKey` — so the route, the component and the tests all read the same constants. `r2.ts` is the only module that touches the SDK, with config resolved lazily (`undefined` unresolved / `null` unconfigured) so an incomplete env never crashes a route at import, which is the mistake `src/lib/email/client.ts` still makes. Object keys are `{userId}/{uuid}{ext}`: the prefix makes ownership visible, the random name means the original filename never reaches the key — nothing to sanitise, and two uploads of `screenshot.png` can't collide — and only the validated extension survives.

**Validation is extension-first, MIME second, and that is the point.** Browsers routinely report an empty string or `application/octet-stream` for `.toml`, `.yaml`, `.md` and `.ini`, so rejecting on an unrecognised MIME type would refuse perfectly valid uploads; a MIME type is only fatal when it is present, specific, and names the *other* kind. **Verified against the real route:** `.toml` with `application/octet-stream` is accepted, while `.md` declared `image/png` is refused. The limit is also enforced on the bytes the handler actually read, which is the same number stored as `fileSize`, so the validated value and the recorded value can never diverge.

**The proxy is where authorisation actually lives.** `getItemByFileKey` scopes by `userId` in the `where` clause, so a foreign key finds no row and answers **404, byte-identical to an unknown key** — the route cannot reveal which objects exist. A cheap key-prefix check short-circuits before any I/O. Crucially this was proved to be the real gate rather than decoration: a key the demo user **owned and had just uploaded** was still refused, because no item referenced it. Responses carry `Content-Security-Policy: default-src 'none'; sandbox` and `nosniff` — `.svg` is executable markup, and while rendering through `<img>` was already safe, direct navigation was not — plus `Cache-Control: private` and both `filename`/`filename*` forms with quotes and separators stripped from the ASCII form.

**`isCreatableType` was replaced by `isUploadType`.** With uploads wired up nothing is uncreatable any more, so the question worth asking is which *kind* of create a type needs; a test pins it against `uploadKindFor` for every system type so the two modules can't disagree. `deleteItem` now returns the key it removed (`{ deleted: true, fileKey }`, distinct from `null` for "no such item") — it has to come back from the delete itself, since the row is gone once it resolves.

**Two defects found in the browser during implementation.** The create dialog's image preview **404'd by design**: it read a pending upload through the proxy, which authorises by finding an item pointing at the key, and no item exists until Create is pressed. Pending uploads now preview from a local `blob:` URL, which is also instant; the drawer still reads through the proxy, where a row does exist. This was a direct consequence of decision (2) and was invisible to unit tests. Separately `fileUrlForKey` had ended up in a component file once the drawer became its only caller, and moved to `uploads.ts`.

**Three more defects found at `review`, each proved with a failing test before the fix.** (1) **`fileName` was unbounded** — a 100,000-character name passed validation, would be written to the column and echoed into the download's `Content-Disposition` as an oversized header; now capped at 255. (2) **The proxy derived the served `Content-Type` from `item.fileName`**, which is client-supplied and never validated, so an uploader could have their `.pdf` object served as `image/svg+xml`; it now derives from the **object key**, whose extension is server-generated and *was* validated at upload. Contained beforehand by the sandbox CSP and `nosniff`, and only against the uploader's own session — but the "derive, don't echo" rule had been applied to the wrong field. (3) **The create action never re-checked the key's extension against the chosen type** — the upload route validates for the type a file was uploaded *as*, which need not be the type the item becomes, so switching type mid-dialog could pair a `.pdf` key with an image item; a new `isExtensionAllowed` is enforced at create.
